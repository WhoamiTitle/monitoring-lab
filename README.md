# Prometheus и Grafana для мониторинга Docker

## Возможности

- Сбор и визуализация четырёх золотых сигналов: задержки, трафика, ошибок и насыщения ресурсов.
- Проверка HTTP-доступности двух приложений с помощью Blackbox Exporter.
- Управляемые сценарии для нагрузки на CPU, память, сеть и диск, а также для имитации задержек и ошибок.
- Автоматическое подключение Prometheus и загрузка дашбордов Grafana.
- Дополнительные графики ресурсов контейнеров через cAdvisor на Linux.

## Что измеряет мониторинг

Метрика — числовое измерение: занятая память, количество запросов или длительность операции. Чтобы увидеть изменения, значения сохраняют вместе со временем. Такой набор называется временным рядом.

У метрики есть имя и labels — метки, различающие объекты. Например:

```text
probe_success{service="web-1"} 1
probe_success{service="web-2"} 1
```

Здесь имя одинаковое, но метки задают два разных ряда. Значение `1` у этой конкретной метрики означает успешную проверку. Само число не имеет универсального смысла: нужно знать назначение метрики и единицы измерения. [Модель данных Prometheus](https://prometheus.io/docs/concepts/data_model/).

## Архитектура Prometheus

Путь данных в практической части:

```text
Запрос → Nginx → журнал завершённых ответов → учебный экспортёр → Prometheus → Grafana
CPU и память → cgroup внутри контейнера → учебный экспортёр → Prometheus → Grafana
Ответ HTTP → Blackbox Exporter → Prometheus → Grafana
Ресурсы Docker → cAdvisor (дополнение для Linux) → Prometheus → Grafana
```

Prometheus периодически делает HTTP-запрос к источнику метрик, получает измерения и сохраняет их во временной базе TSDB. В стенде интервал равен пяти секундам. Этот способ сбора называется pull: инициатор запроса — Prometheus. При необходимости цели находят через service discovery; в стенде адреса перечислены явно. [Архитектура Prometheus](https://prometheus.io/docs/introduction/overview/).

Каждый `web` — Nginx с небольшим учебным экспортёром `web/exporter.py` в том же контейнере. Nginx пишет HTTP-статус и время завершённого запроса в отдельный журнал, экспортёр строит счётчики и гистограмму и читает cgroup своего контейнера. Он отдаёт метрики на порт 9117 внутри сети Compose. Docker socket и привилегированный доступ ему не нужны. Экспортёр создан для демонстрации, а не для промышленной эксплуатации.

cAdvisor считывает сведения о ресурсах контейнеров и публикует их на `/metrics`. Экспортер — компонент, который делает показатели системы доступными для мониторинга. [Руководство по cAdvisor](https://prometheus.io/docs/guides/cadvisor/).

Blackbox Exporter проверяет HTTP-адрес приложения по запросу Prometheus. Он позволяет узнать, отвечает ли приложение, даже если приложение не умеет отдавать собственные метрики. [Blackbox Exporter](https://github.com/prometheus/blackbox_exporter).

Grafana обращается к Prometheus, выполняет запросы и рисует панели. Dashboard — страница с несколькими панелями; data source — подключённый источник данных. В этом стенде источник и панели загружаются из файлов автоматически. [Настройка Grafana из файлов](https://grafana.com/docs/grafana/latest/administration/provisioning/).

PromQL — язык запросов к метрикам Prometheus. Один запрос может выбрать ряд, вычислить скорость роста счётчика или объединить значения нескольких контейнеров. [Основы PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/).

Для оповещений Prometheus вычисляет alerting rules. Alertmanager получает сработавшие оповещения и управляет их группировкой, подавлением и отправкой. Его можно добавить после основной демонстрации; в этот стенд он не включён. [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/).

## Типы метрик

| Тип | Что показывает | Пример |
| --- | --- | --- |
| Counter | Накопленный итог, который растёт и может сброситься при перезапуске | Всего принятых байтов, запросов, секунд CPU |
| Gauge | Текущее значение, которое может расти и уменьшаться | Занятая RAM, температура, активные соединения |
| Histogram | Распределение наблюдений по диапазонам | Длительность HTTP-запросов |
| Summary | Число и сумма наблюдений, а в поддерживающих это библиотеках — квантили, вычисляемые приложением | Задержки операций |

Для CPU и сети используется Counter: значение «всего байтов за всё время» переводят в скорость функцией `rate`. Для памяти используется Gauge: текущее значение можно рисовать непосредственно.

Histogram помогает ответить на вопрос «какая задержка у 95% запросов?». Для классической Histogram границы диапазонов задаются заранее; Prometheus оценивает квантиль по ним. Есть также native histograms. Квантили Summary, рассчитанные разными экземплярами приложения, нельзя просто усреднить и получить общий p95. [Типы метрик](https://prometheus.io/docs/concepts/metric_types/), [Histogram и Summary](https://prometheus.io/docs/practices/histograms/).

## Запуск стенда

Для запуска требуются Docker и Docker Compose. Клонирование репозитория и запуск базового стенда:

```bash
git clone https://github.com/WhoamiTitle/monitoring-lab.git
cd monitoring-lab
docker compose --profile load up -d --build
docker compose --profile load ps
```

Первому запуску нужен интернет для загрузки образов и сборки учебного образа Nginx с Python. Для Windows предусмотрен запуск через Docker Desktop с WSL 2 и терминал WSL; работоспособность на конкретной Windows-машине требует отдельной проверки.

В составе базовой части:

- `web-1` и `web-2` — два небольших приложения Nginx;
- `blackbox` — проверка их HTTP-ответов;
- `prometheus` — сбор и хранение измерений;
- `grafana` — отображение данных;
- `load` — необязательный генератор HTTP-запросов, включаемый профилем `load`.

Доступные адреса:

| Сервис | Адрес |
| --- | --- |
| Prometheus | [localhost:9090](http://localhost:9090) |
| Grafana | [localhost:3000](http://localhost:3000) |
| Первое приложение | [localhost:8081](http://localhost:8081) |
| Второе приложение | [localhost:8082](http://localhost:8082) |

Начальные данные для входа в Grafana: `admin` / `learning-demo`. Если том Grafana уже содержит изменённую учётную запись, используются данные из существующей базы. Порты стенда привязаны к `127.0.0.1`.

В папке Grafana **Monitoring Demo** доступны дашборды **Четыре золотых сигнала** и **Доступность приложений**. Оба подключены к Prometheus. Дашборд сигналов по умолчанию показывает последние 5 минут и обновляется каждые 5 секунд.

## Четыре золотых сигнала

Для демонстрации используется включённый фоновый `load`. Сценарии выполняются из корня проекта:

| Сигнал | Команда | Что увидеть |
| --- | --- | --- |
| Задержка | `./demo.sh slow web-1 30` | Для `web-1 / slow / 2xx` появляется p95 медленных ответов. |
| Трафик | `./demo.sh traffic web-1 30` | Растёт количество завершённых HTTP-запросов в секунду у `web-1`. |
| Ошибки | `./demo.sh errors web-2 30` | Растёт доля ответов 5xx у `web-2`. |
| Насыщение | `./demo.sh cpu web-1 30` | Использование CPU `web-1` растёт относительно лимита. |
| Насыщение | `./demo.sh memory web-2 30` | Использование памяти `web-2` растёт на время сценария. |

Дашборд использует окно `rate` в 30 секунд; изменения появляются постепенно после нескольких опросов. p95 — приближённая оценка по корзинам гистограммы; успешные и ошибочные ответы разделены. В трафик входят фоновые запросы и проверки Blackbox. Доля 5xx измеряется среди завершённых ответов Nginx; если запросы не доходят до остановленного приложения, это показывает отдельная панель Blackbox. Память cgroup включает файловый кэш и tmpfs, а CPU и память учитывают также сам учебный экспортёр. Высокое использование ресурса само по себе не доказывает наличие узкого места.

При `docker compose stop web-1` панель доступности покажет отказ, а `docker compose start web-1` восстановит сервис. При отсутствии HTTP-запросов или недоступных cgroup возможны `No data`; это не нулевое значение.

[Четыре золотых сигнала в книге Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/), [гистограммы Prometheus](https://prometheus.io/docs/practices/histograms/), [метрики контейнеров Docker](https://docs.docker.com/engine/containers/runmetrics/).

Для самостоятельного создания панели используются источник **Prometheus**, тип **Time series** и режим запроса **Code**. Внутренний адрес источника — `http://prometheus:9090`: контейнеры обращаются друг к другу по именам сервисов Compose.

## Первые запросы PromQL

В интерфейсе Prometheus доступен запрос состояния целей сбора:

```promql
up
```

`up = 1` означает, что Prometheus успешно получил метрики от соответствующей цели; `up = 0` — сбор не удался. Это не универсальная проверка работоспособности приложения. [Jobs и instances](https://prometheus.io/docs/concepts/jobs_instances/).

Результаты HTTP-проверок приложений:

```promql
probe_success{job="web-http"}
```

Ожидаются два ряда со значением `1`. Чтобы выбрать только первое приложение:

```promql
probe_success{job="web-http",service="web-1"}
```

В интерфейсе Prometheus результаты доступны как текущее значение и как график за выбранный период.

## Остановка контейнера

Остановка первого приложения:

```bash
docker compose stop web-1
```

После очередной проверки и обновления панели `probe_success` для `web-1` должно стать `0`, а для `web-2` — остаться `1`. Изменение обычно отображается через 10–20 секунд.

Восстановление приложения:

```bash
docker compose start web-1
```

После следующей успешной проверки значение вернётся к `1`.

При этом `up{job="web-http",service="web-1"}` может оставаться равным `1`: Prometheus успешно получил отчёт Blackbox Exporter о неуспешной HTTP-проверке. `up{job="cadvisor"}` при работе Linux-дополнения также останется `1`, пока отвечает сам cAdvisor. Состояние источника метрик и результат проверки приложения — разные показатели. [Описание Blackbox Exporter](https://github.com/prometheus/blackbox_exporter).

## Ресурсы контейнеров на Linux

Для этой части нужен обычный Docker Engine на Linux с доступом к cgroups и каталогам Docker. Docker Desktop запускает контейнеры внутри Linux VM; это влияет на пути и доступность системных показателей. Поэтому Linux-дополнение не включается автоматически на Mac и Windows. [Устройство Docker Desktop](https://docs.docker.com/desktop/features/networking/).

Для запуска Linux-дополнения из корня проекта:

```bash
docker compose -f compose.yaml -f compose.linux.yaml --profile load up -d
```

Дополнение добавляет cAdvisor, его цель сбора и дашборд **Ресурсы Docker контейнеров**. Для расчёта `rate` необходимо дождаться накопления измерений; обычно достаточно одной-двух минут.

В дополнении используются стандартные пути `/var/lib/docker`, `/sys` и `/dev/kmsg`. Если Docker настроен с другим `DockerRootDir`, требуется изменить соответствующий mount в `compose.linux.yaml`; rootless Docker требует отдельной настройки доступа. cAdvisor запускается с системными правами для чтения показателей. [Инструкция cAdvisor](https://github.com/google/cadvisor).

Порты стенда доступны только локально. Для работы с удалённым Linux можно использовать SSH-туннель, указав вместо `user@server` адрес сервера:

```bash
ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 user@server
```

После этого Grafana и Prometheus доступны на `localhost` компьютера, с которого установлен SSH-туннель.

**Управляемая нагрузка.** Примеры запуска из корня проекта для работающего `web-1`:

```bash
./demo.sh cpu web-1
./demo.sh memory web-1
./demo.sh traffic web-1
./demo.sh disk web-1
```

По умолчанию CPU нагружается 20 секунд; RAM занимает дополнительные 32 MiB на 30 секунд; диск получает файл 16 MiB на 30 секунд; дополнительные HTTP-запросы идут 20 секунд. Временные файлы удаляются после завершения. Сценарий можно досрочно остановить через `Ctrl+C`: созданная им нагрузка будет остановлена, а временные ресурсы удалены. Необязательный третий аргумент задаёт длительность в секундах от 1 до 120, например `./demo.sh memory web-2 45`. Все режимы описаны в `./demo.sh --help`.

CPU, память и диск нагружаются внутри выбранного контейнера. Для сетевого сценария создаётся временный клиент из сервиса `load`: он обращается только к указанному приложению и удаляется после работы. Сценарии можно запускать с Docker Desktop или Linux; подробный дашборд CPU, RAM, сети и диска использует Linux-дополнение с cAdvisor. На базовом дашборде CPU и память видны и без cAdvisor, сетевой сигнал там выражен HTTP-запросами, а график дисковых байтов не добавляется.

### CPU

```promql
100 * sum by (container_label_monitoring_demo) (
  rate(container_cpu_usage_seconds_total{
    job="cadvisor",
    container_label_monitoring_demo=~"web-1|web-2"
  }[1m])
)
```

`rate` оценивает прирост в секунду за последнюю минуту и учитывает сбросы счётчика. Например, две секунды CPU за пять секунд реального времени соответствуют в среднем 40% одного ядра. В стенде каждому веб-контейнеру разрешено одно ядро. Для контейнера без такого ограничения показатель может превышать 100%. [Функция rate](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate).

Для создания процессорной нагрузки в первом контейнере:

```bash
./demo.sh cpu web-1
```

Процесс завершится автоматически через 20 секунд. На графике с окном `[1m]` подъём сглаживается по минуте.

### RAM

```promql
container_memory_working_set_bytes{
  job="cadvisor",
  container_label_monitoring_demo=~"web-1|web-2"
}
```

Это оценка working set в байтах. Она может включать часть файлового кэша и не равна строго памяти RSS. Grafana переводит байты в удобные единицы отображения.

Чтобы временно занять 32 MiB в `/dev/shm` первого контейнера:

```bash
./demo.sh memory web-1
```

Через 30 секунд файл в tmpfs автоматически удалится. Это нагрузка на память контейнера, а не увеличение памяти процесса Nginx.

### Сеть

```promql
sum by (container_label_monitoring_demo) (
  rate(container_network_receive_bytes_total{
    job="cadvisor",
    container_label_monitoring_demo=~"web-1|web-2"
  }[1m])
)
```

Результат — входящий трафик в байтах в секунду. Для исходящего трафика в имени метрики используется `transmit` вместо `receive`. Генератор `load` создаёт небольшое движение на этих графиках.

Для дополнительного трафика только к первому приложению:

```bash
./demo.sh traffic web-1
```

### Диск

Занятое место и скорость операций — разные характеристики. В дашборде есть обе:

- `container_fs_usage_bytes` — занимаемый объём в байтах;
- `rate(container_fs_reads_bytes_total[1m])` — скорость чтения;
- `rate(container_fs_writes_bytes_total[1m])` — скорость записи.

У запросов в дашборде добавлены те же фильтры контейнеров, что и у CPU. Набор дисковых показателей зависит от ядра, cgroups и драйвера хранения Docker. Чтение из кэша может не вызывать обращения к диску. Отсутствие метрики отображается как **No data**; его нельзя интерпретировать как нулевую нагрузку. [Список метрик cAdvisor](https://github.com/google/cadvisor/blob/master/docs/storage/prometheus.md).

Чтобы записать 16 MiB внутри первого контейнера и оставить файл на время наблюдения:

```bash
./demo.sh disk web-1
```

Скрипт удалит созданный им файл автоматически после 30 секунд.

После остановки контейнера новые измерения его ресурсов прекращаются. В зависимости от задержек сбора и запросов линия может закончиться с небольшой задержкой. История останется в Prometheus, а панели `rate` могут ещё кратко использовать измерения из своего окна. Разрыв линии не равен нулю; для демонстрации остановки используется отдельная HTTP-проверка. [Устаревание рядов](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness).

## Применение мониторинга

Ресурсные метрики помогают найти узкое место: занятый CPU, растущую память, перегруженную сеть или диск. Метрики приложения дополняют картину: сколько запросов оно обслуживает, сколько ошибок возникает и насколько долго выполняются операции. Поэтому при росте времени ответа полезно одновременно смотреть нагрузку и состояние приложения.

В учебном проекте удобно начать с четырёх сигналов и дополнить их независимой проверкой доступности. Оповещение о недоступности можно добавить следующим шагом, когда понятна метрика, по которой оно должно срабатывать.
