# Prometheus и Grafana для мониторинга Docker

Этот стенд поможет разобраться, как собираются метрики, как читать графики и как заметить остановку приложения. Docker Compose уже знаком тебе, поэтому начинаем с устройства мониторинга.

Базовая часть запускается в Docker Desktop и показывает доступность двух приложений. Дополнение с cAdvisor предназначено для обычного Docker Engine на Linux и добавляет CPU, RAM, сеть и диск. Для представления проекта нужны обе части: состояние ресурсов и проверка того, что приложение отвечает.

## Порядок изучения

1. Разобраться в ролях Prometheus, экспортера и Grafana.
2. Освоить Counter и Gauge на конкретных значениях.
3. Запустить базовый стенд и посмотреть метрики в Prometheus.
4. Открыть те же данные в Grafana, остановить и запустить приложение.
5. На Linux добавить cAdvisor и изучить ресурсы контейнеров.
6. Узнать назначение Histogram, Summary и оповещений, затем подготовить рассказ о проекте.

После первого прохода ты должен уметь объяснить путь одного измерения от контейнера до графика и показать, по каким данным обнаруживается остановка приложения.

## Что измеряет мониторинг

Метрика — числовое измерение: занятая память, количество запросов или длительность операции. Чтобы увидеть изменения, значения сохраняют вместе со временем. Такой набор называется временным рядом.

У метрики есть имя и labels — метки, различающие объекты. Например:

```text
probe_success{service="web-1"} 1
probe_success{service="web-2"} 1
```

Здесь имя одинаковое, но метки задают два разных ряда. Значение `1` у этой конкретной метрики означает успешную проверку. Само число не имеет универсального смысла: нужно знать назначение метрики и единицы измерения. [Модель данных Prometheus](https://prometheus.io/docs/concepts/data_model/).

## Архитектура Prometheus

Путь данных в практической части:

```text
Ресурсы Docker → cAdvisor → Prometheus → Grafana
Ответ HTTP    → Blackbox Exporter → Prometheus → Grafana
```

Prometheus периодически делает HTTP-запрос к источнику метрик, получает измерения и сохраняет их во временной базе TSDB. В нашем стенде интервал равен пяти секундам. Этот способ сбора называется pull: инициатор запроса — Prometheus. При необходимости цели находят через service discovery; в стенде адреса перечислены явно. [Архитектура Prometheus](https://prometheus.io/docs/introduction/overview/).

cAdvisor считывает сведения о ресурсах контейнеров и публикует их на `/metrics`. Экспортер — компонент, который делает показатели системы доступными для мониторинга. [Руководство по cAdvisor](https://prometheus.io/docs/guides/cadvisor/).

Blackbox Exporter проверяет HTTP-адрес приложения по запросу Prometheus. Он позволяет узнать, отвечает ли приложение, даже если приложение не умеет отдавать собственные метрики. [Blackbox Exporter](https://github.com/prometheus/blackbox_exporter).

Grafana обращается к Prometheus, выполняет запросы и рисует панели. Dashboard — страница с несколькими панелями; data source — подключённый источник данных. В этом стенде источник и панели загружаются из файлов автоматически. [Настройка Grafana из файлов](https://grafana.com/docs/grafana/latest/administration/provisioning/).

PromQL — язык запросов к метрикам Prometheus. Один запрос может выбрать ряд, вычислить скорость роста счётчика или объединить значения нескольких контейнеров. [Основы PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/).

Для оповещений Prometheus вычисляет alerting rules. Alertmanager получает сработавшие оповещения и управляет их группировкой, подавлением и отправкой. Его можно добавить после основной демонстрации; в этот стенд он не включён. [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/).

## Типы метрик

| Тип | Что показывает | Пример |
| --- | --- | --- |
| Counter | Накопленный итог, который растёт и может сброситься при перезапуске | Всего принятых байтов, запросов, секунд CPU |
| Gauge | Текущее значение, которое может расти и уменьшаться | Занятая RAM, температура, активные соединения |
| Histogram | Распределение наблюдений по диапазонам | Длительность HTTP-запросов |
| Summary | Число и сумма наблюдений, а в поддерживающих это библиотеках — квантили, вычисляемые приложением | Задержки операций |

Для CPU и сети используется Counter: значение «всего байтов за всё время» переводят в скорость функцией `rate`. Для памяти используется Gauge: текущее значение можно рисовать непосредственно.

Histogram помогает ответить на вопрос «какая задержка у 95% запросов?». Для классической Histogram границы диапазонов задаются заранее; Prometheus оценивает квантиль по ним. Есть также native histograms. Квантили Summary, рассчитанные разными экземплярами приложения, нельзя просто усреднить и получить общий p95. На первом этапе достаточно понимать назначение этих типов. [Типы метрик](https://prometheus.io/docs/concepts/metric_types/), [Histogram и Summary](https://prometheus.io/docs/practices/histograms/).

## Запуск первой практики

В терминале перейди в папку стенда:

```bash
cd '/Users/vasiliy/Documents/monitoring-lab'
docker compose --profile load up -d
docker compose ps
```

На другом компьютере используй путь к скопированной папке. Первому запуску нужен интернет для загрузки образов.

В составе базовой части:

- `web-1` и `web-2` — два небольших приложения Nginx;
- `blackbox` — проверка их HTTP-ответов;
- `prometheus` — сбор и хранение измерений;
- `grafana` — отображение данных;
- `load` — необязательный генератор HTTP-запросов, включаемый профилем `load`.

Открой:

| Сервис | Адрес |
| --- | --- |
| Prometheus | [localhost:9090](http://localhost:9090) |
| Grafana | [localhost:3000](http://localhost:3000) |
| Первое приложение | [localhost:8081](http://localhost:8081) |
| Второе приложение | [localhost:8082](http://localhost:8082) |

Вход в Grafana: `admin` / `learning-demo`. Это учётная запись локального учебного стенда; порты привязаны к `127.0.0.1`.

В Grafana открой папку **Monitoring Demo**, затем дашборд **Доступность приложений**. Он уже подключён к Prometheus. Оставь диапазон последних 15 минут и обновление каждые 5 секунд.

Если собираешь панель самостоятельно, выбери источник **Prometheus**, тип **Time series**, затем режим запроса **Code** и вставь запрос из следующих примеров. Внутренний адрес источника — `http://prometheus:9090`: контейнеры обращаются друг к другу по именам сервисов Compose.

## Первые запросы PromQL

В интерфейсе Prometheus введи:

```promql
up
```

Ты увидишь цели сбора. `up = 1` означает, что Prometheus успешно получил метрики от соответствующей цели; `up = 0` — сбор не удался. Это не универсальная проверка работоспособности приложения. [Jobs и instances](https://prometheus.io/docs/concepts/jobs_instances/).

Затем выполни:

```promql
probe_success{job="web-http"}
```

Ожидаются два ряда со значением `1`. Чтобы выбрать только первое приложение:

```promql
probe_success{job="web-http",service="web-1"}
```

Сначала посмотри текущее значение, затем переключись на график. Так ты увидишь разницу между измерением в данный момент и его историей.

## Остановка контейнера

1. Убедись, что оба приложения показывают «Доступен».
2. Сохрани скриншот дашборда до остановки.
3. Выполни:

```bash
docker compose stop web-1
```

4. Подожди примерно 10–20 секунд: нужны очередная проверка и обновление панели.
5. У `web-1` значение `probe_success` должно стать `0`; у `web-2` оно должно остаться `1`.
6. Сохрани скриншот. Затем восстанови контейнер:

```bash
docker compose start web-1
```

После следующей успешной проверки значение вернётся к `1`.

При этом `up{job="web-http",service="web-1"}` может оставаться равным `1`: Prometheus успешно получил отчёт Blackbox Exporter о неуспешной HTTP-проверке. `up{job="cadvisor"}` при работе Linux-дополнения также останется `1`, пока отвечает сам cAdvisor. Состояние источника метрик и результат проверки приложения — разные показатели. [Описание Blackbox Exporter](https://github.com/prometheus/blackbox_exporter).

## Ресурсы контейнеров на Linux

Для этой части нужен обычный Docker Engine на Linux с доступом к cgroups и каталогам Docker. Docker Desktop запускает контейнеры внутри Linux VM; это влияет на пути и доступность системных показателей. Поэтому Linux-дополнение не включается автоматически на Mac и Windows. [Устройство Docker Desktop](https://docs.docker.com/desktop/features/networking/).

Скопируй папку стенда на Linux, перейди в неё и выполни:

```bash
docker compose -f compose.yaml -f compose.linux.yaml --profile load up -d
```

Открой второй дашборд **Ресурсы Docker контейнеров**. Дай ему одну-две минуты накопить измерения для `rate`. Этот запуск добавляет cAdvisor, его цель сбора и панели ресурсов.

В дополнении используются стандартные пути `/var/lib/docker`, `/sys` и `/dev/kmsg`. Если Docker настроен с другим `DockerRootDir`, измени соответствующий mount в `compose.linux.yaml`; rootless Docker требует отдельной настройки доступа. cAdvisor запускается с системными правами для чтения показателей. [Инструкция cAdvisor](https://github.com/google/cadvisor).

Порты стенда доступны только локально. При работе на удалённом Linux используй SSH-туннель, заменив `user@server` своим адресом:

```bash
ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 user@server
```

После этого Grafana и Prometheus откроются на `localhost` твоего компьютера.

**Управляемая нагрузка.** Из корня проекта запусти любой сценарий для работающего `web-1` или `web-2`:

```bash
./demo.sh cpu web-1
./demo.sh memory web-1
./demo.sh traffic web-1
./demo.sh disk web-1
```

По умолчанию CPU нагружается 20 секунд; RAM занимает дополнительные 32 MiB на 30 секунд; диск получает файл 16 MiB на 30 секунд; дополнительные HTTP-запросы идут 20 секунд. Временные файлы удаляются после завершения. Сценарий можно досрочно остановить через `Ctrl+C`: созданная им нагрузка будет остановлена, а временные ресурсы удалены. Необязательный третий аргумент задаёт длительность в секундах от 1 до 120, например `./demo.sh memory web-2 45`. Все режимы описаны в `./demo.sh --help`.

CPU, память и диск нагружаются внутри выбранного контейнера. Для сетевого сценария создаётся временный клиент из сервиса `load`: он обращается только к указанному приложению и удаляется после работы. Сценарии можно запускать с Docker Desktop или Linux; ресурсный дашборд этого стенда использует Linux-дополнение с cAdvisor.

### CPU

```promql
100 * sum by (container_label_monitoring_demo) (
  rate(container_cpu_usage_seconds_total{
    job="cadvisor",
    container_label_monitoring_demo=~"web-1|web-2"
  }[1m])
)
```

`rate` оценивает прирост в секунду за последнюю минуту и учитывает сбросы счётчика. Например, две секунды CPU за пять секунд реального времени соответствуют в среднем 40% одного ядра. В стенде каждому веб-контейнеру разрешено одно ядро. Для контейнера без такого ограничения показатель может превышать 100%. [Функция rate](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate).

Чтобы увидеть подъём CPU первого контейнера, запусти:

```bash
./demo.sh cpu web-1
```

Процесс завершится автоматически через 20 секунд. На графике с окном `[1m]` подъём сглаживается по минуте.

### RAM

```promql
container_memory_working_set_bytes{
  job="cadvisor",
  container_label_monitoring_demo=~"web-1|web-2"
}
```

Это оценка working set в байтах. Она может включать часть файлового кэша и не равна строго памяти RSS. Grafana переводит байты в удобные единицы отображения.

Чтобы временно занять 32 MiB в `/dev/shm` первого контейнера:

```bash
./demo.sh memory web-1
```

Через 30 секунд файл в tmpfs автоматически удалится. Это нагрузка на память контейнера, а не увеличение памяти процесса Nginx.

### Сеть

```promql
sum by (container_label_monitoring_demo) (
  rate(container_network_receive_bytes_total{
    job="cadvisor",
    container_label_monitoring_demo=~"web-1|web-2"
  }[1m])
)
```

Результат — входящий трафик в байтах в секунду. Для исходящего замени `receive` на `transmit` в имени метрики. Генератор `load` создаёт небольшое движение на этих графиках.

Для дополнительного трафика только к первому приложению:

```bash
./demo.sh traffic web-1
```

### Диск

Занятое место и скорость операций — разные характеристики. В дашборде есть обе:

- `container_fs_usage_bytes` — занимаемый объём в байтах;
- `rate(container_fs_reads_bytes_total[1m])` — скорость чтения;
- `rate(container_fs_writes_bytes_total[1m])` — скорость записи.

У запросов в дашборде добавлены те же фильтры контейнеров, что и у CPU. Набор дисковых показателей зависит от ядра, cgroups и драйвера хранения Docker. Чтение из кэша может не вызывать обращения к диску. Отсутствие метрики отображается как **No data**; его нельзя интерпретировать как нулевую нагрузку. [Список метрик cAdvisor](https://github.com/google/cadvisor/blob/master/docs/storage/prometheus.md).

Чтобы записать 16 MiB внутри первого контейнера и оставить файл на время наблюдения:

```bash
./demo.sh disk web-1
```

Скрипт удалит созданный им файл автоматически после 30 секунд.

После остановки контейнера новые измерения его ресурсов прекращаются. В зависимости от задержек сбора и запросов линия может закончиться с небольшой задержкой. История останется в Prometheus, а панели `rate` могут ещё кратко использовать измерения из своего окна. Разрыв линии не равен нулю; для демонстрации остановки опирайся на отдельную HTTP-проверку. [Устаревание рядов](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness).

## Применение мониторинга

Ресурсные метрики помогают найти узкое место: занятый CPU, растущую память, перегруженную сеть или диск. Метрики приложения дополняют картину: сколько запросов оно обслуживает, сколько ошибок возникает и насколько долго выполняются операции. Поэтому при росте времени ответа полезно одновременно смотреть нагрузку и состояние приложения.

Для учебного проекта достаточно двух вопросов: «как меняется потребление ресурсов?» и «остаётся ли приложение доступным?». Оповещение о недоступности можно добавить следующим шагом, когда понятна метрика, по которой оно должно срабатывать.

## План представления проекта

1. Объясни задачу: наблюдать за контейнерами и заметить недоступность приложения.
2. Покажи путь данных и роли Prometheus, cAdvisor, Blackbox Exporter и Grafana.
3. Сравни четыре типа метрик; отдельно объясни, почему CPU и сеть требуют `rate`.
4. Покажи панели CPU, RAM, сети и диска на работающем стенде Linux.
5. Останови `web-1`, покажи изменение его доступности и сохранение доступности `web-2`.
6. Объясни, почему cAdvisor может оставаться доступным, а ресурсные линии перестают получать новые точки.
7. Запусти `web-1` и покажи восстановление.

Формулировка, которую стоит уметь произнести своими словами: «Prometheus собирает и хранит измерения. cAdvisor предоставляет показатели контейнеров. Grafana показывает данные из Prometheus. Для проверки ответа приложения мы используем отдельную HTTP-проверку».

## Если графиков нет

- Выполни `docker compose ps` и проверь, что нужные сервисы запущены.
- Открой в Prometheus страницу **Targets**: у каждой цели видна ошибка последнего сбора.
- Начни с `up` и `probe_success`, затем переходи к ресурсным запросам.
- Для `rate` подожди накопления нескольких измерений.
- На Linux проверь `up{job="cadvisor"}` и запрос `container_last_seen{container_label_monitoring_demo=~"web-1|web-2"}`. Если меток нет, проверь журналы cAdvisor и пути mounts.
- Если заняты порты 3000, 9090, 8081 или 8082, поменяй внешние порты в `compose.yaml` и адреса, которые открываешь в браузере.
- Для файлового дашборда изменения через UI сохраняй как копию или экспортируй в JSON: повторное provisioning может заменить редактирование конфигурацией из файла.

## Завершение работы

Для базовой части:

```bash
docker compose --profile load down
```

Для Linux-дополнения:

```bash
docker compose -f compose.yaml -f compose.linux.yaml --profile load down
```

История и настройки сохраняются в именованных volumes. Удаление volumes с флагом `-v` удалит эти учебные данные. Prometheus хранит историю до семи дней согласно настройке стенда.
